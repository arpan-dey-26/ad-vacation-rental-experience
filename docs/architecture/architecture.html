Scope

Everything on this page is a recommendation except one box. StayVista as submitted is a desktop front end with a frontend-held data layer and no backend at all — the single node outlined in green. It implements no service, database, queue or integration shown here. The diagram answers the assignment's request for a production-scale architecture; it does not claim the clone implements it. Flows are explained in docs/15-production-architecture.md.

Data

Primary relational DB Per-service schemas; bookings strongly consistent
Read replicas Listing and review reads; replica lag budgeted
Cache Hot listings, pricing, session data; TTL + event bust
Search index Denormalised documents, rebuilt from events

Analytics / event store Append-only; warehouse and ML features

Backups & PITR Cross-region, restore-tested

Principal flows — detailed in docs/15-production-architecture.md

  1. Browse / search. Client → CDN/WAF → API gateway → Search → search index → Listing → cache, then replica on miss → response. Cache and index absorb read traffic; the primary database is not on this path.
  2. Listing photos. Client → CDN → object storage on miss. Images never transit an application service. StayVista links to the reference origin at runtime and packages nothing.
  3. Booking. Client → gateway → Booking → Availability (transactional hold) → Pricing → Payment → PSP → booking database → event bus → notifications. Idempotency keys make a retried request safe; the hold is what prevents double-selling.
  4. Host listing update. Host → Host/Admin → Listing → database → event bus → search re-index and media processing → CDN invalidation. Search is eventually consistent by design.
  5. Reviews. Guest → Review → moderation → database → event pipeline → rating aggregates on the listing. Aggregates are recomputed asynchronously, never in the write path.
